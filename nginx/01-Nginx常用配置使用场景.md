# Nginx 常用配置的使用场景

Nginx 的配置，本质上是在入口流量到达业务服务之前，对请求进行接收、判断、转发、限制和记录。实际使用时，应先明确要解决的问题，再决定需要哪些能力，而不是把所有配置都堆在一起。

本文只说明常用配置的使用场景、选择依据和注意事项，不提供具体配置代码。

## 1. 静态网站与静态资源托管

### 适用场景

- 部署纯 HTML、CSS、JavaScript 网站。
- 托管图片、字体、安装包、说明文档等静态文件。
- 前后端分离项目中，由 Nginx 提供前端构建产物。
- 将不需要业务计算的资源直接返回，避免请求进入应用服务器。

### 解决的问题

静态文件不需要经过 Java、Node.js、Python 等应用程序处理。由 Nginx 直接读取并返回，可以减少应用服务器的连接数和计算开销，并提高资源响应速度。

### 注意事项

- 应区分 HTML 与带版本号的静态资源。HTML 通常需要较短缓存，而文件名中带内容哈希的 JavaScript、CSS 和图片可以长期缓存。
- 需要防止用户通过路径访问站点根目录之外的文件。
- 大文件下载要考虑磁盘吞吐量、并发连接数和断点续传需求。
- 如果资源已经放在对象存储或 CDN 中，Nginx 不一定还需要承担静态文件分发工作。

## 2. 反向代理应用服务

### 适用场景

- 用户访问统一域名，由 Nginx 将请求转发给后端应用。
- 后端服务只监听内网地址，不直接暴露到互联网。
- 同一入口代理 Java、Node.js、Python、Go 等不同技术栈的服务。
- 希望统一处理 HTTPS、访问日志、请求头和错误页面。

### 解决的问题

反向代理可以隐藏后端服务的真实地址，使客户端只与 Nginx 通信。Nginx 负责接收外部连接，后端应用专注于业务逻辑。

### 注意事项

- 后端通常需要获得原始客户端 IP、访问协议和域名，否则日志、鉴权或重定向可能出现错误。
- 应明确连接超时、响应超时和请求体大小，避免使用不符合业务特征的统一数值。
- 后端故障时，需要准备明确的错误响应或降级页面。
- 反向代理不是防火墙，也不能代替应用自身的身份认证和权限控制。

## 3. 多实例负载均衡

### 适用场景

- 同一个应用部署了多个实例，需要分摊请求。
- 单台服务器无法承担当前访问量。
- 希望某个实例维护或故障时，其他实例继续提供服务。
- 灰度发布期间，需要把部分流量导向新版本。

### 解决的问题

Nginx 可以在多个后端实例之间分配请求，提高整体吞吐量和可用性，并降低单个实例成为瓶颈的风险。

### 注意事项

- 应优先将会话、文件和状态放到共享存储或外部服务中，使应用实例尽量无状态。
- 如果业务依赖本地会话，可能需要会话保持，但这会降低流量调度的灵活性。
- 负载均衡不等于健康检查。必须明确实例失效后如何发现、摘除和恢复。
- 长请求和短请求混合时，简单轮询可能造成实例负载不均。
- 数据库连接、消息队列和共享缓存也可能成为扩容后的新瓶颈。

## 4. HTTPS 入口与 TLS 终止

### 适用场景

- 网站需要通过 HTTPS 对外提供服务。
- 多个后端应用希望统一管理证书和加密策略。
- 内部应用只处理 HTTP，由 Nginx 负责外部 TLS 握手。
- 需要将 HTTP 请求统一跳转到 HTTPS。

### 解决的问题

将证书和 TLS 配置集中在 Nginx，可以减少每个应用重复管理证书的成本，并统一安全策略。

### 注意事项

- 证书必须在过期前完成续签和加载，并监控续签是否成功。
- 后端需要知道客户端原始访问协议是 HTTPS，避免产生错误的 HTTP 跳转地址。
- TLS 终止后，Nginx 到后端之间是否继续加密，应根据网络边界和合规要求决定。
- 不应继续启用已经淘汰的协议版本和弱加密套件。

## 5. 域名与路径路由

### 适用场景

- 不同域名对应不同网站或业务系统。
- 同一域名下，`/api`、`/admin`、`/static` 等路径由不同服务处理。
- 单体系统拆分为多个服务后，仍需要对外提供统一入口。
- 多租户系统根据域名区分客户站点。

### 解决的问题

Nginx 可以依据域名和请求路径选择目标服务，使多个系统共享有限的公网入口，并保持对外 URL 稳定。

### 注意事项

- 路径匹配存在优先级，规则重叠时容易把请求转发到错误位置。
- 转发前是否去掉路径前缀必须明确，否则后端收到的路径可能与预期不同。
- 应统一尾部斜杠策略，避免重复跳转或同一内容出现多个 URL。
- 域名路由需要设置明确的默认站点，防止未知域名误入正式业务。

## 6. 单页应用的前端路由回退

### 适用场景

- 使用 React、Vue、Angular 等框架构建单页应用。
- 用户直接访问前端路由或刷新页面时，服务器找不到对应的物理文件。
- 前端路由由浏览器负责，但静态资源仍由 Nginx 提供。

### 解决的问题

当请求不是实际存在的静态文件时，将页面请求回退到前端入口文件，再由前端路由决定显示内容。

### 注意事项

- 回退不能覆盖 API、图片和其他真实资源路径，否则接口错误可能被错误地返回成 HTML。
- 入口 HTML 不宜长期缓存，否则发布新版本后用户可能仍引用旧资源。
- 真实不存在的静态资源应返回正确的错误状态，而不是全部回退到首页。

## 7. 缓存静态资源或代理响应

### 适用场景

- 图片、CSS、JavaScript 等资源被频繁重复访问。
- 后端生成某些公开内容的成本较高，但内容短时间内变化不频繁。
- 希望减少回源请求和后端压力。
- 上游服务短暂不可用时，希望在一定条件下继续返回已有内容。

### 解决的问题

合理缓存可以缩短响应时间、降低网络传输和后端计算压力，并提高高流量场景下的稳定性。

### 注意事项

- 包含用户身份、权限或个性化信息的响应通常不能直接共享缓存。
- 必须明确缓存键包含哪些因素，例如域名、路径、查询参数和请求头。
- 应设计缓存更新和失效机制，避免内容长期不一致。
- 不要缓存登录、支付、管理后台等敏感接口。
- CDN 更适合全球范围的大规模静态内容分发，Nginx 本地缓存不能完全替代 CDN。


## 9. 请求限速、限流与并发控制

### 适用场景

- 登录、注册、短信验证码等接口需要防止高频调用。
- 爬虫或异常客户端大量访问，影响正常用户。
- 后端服务容量有限，需要削平突发流量。
- 下载服务需要限制单连接速度或总体并发。

### 解决的问题

限流和并发控制可以保护后端资源，降低突发请求导致服务雪崩的风险，并限制明显异常的访问行为。

### 注意事项

- 限流维度可能是客户端 IP、用户、接口或业务标识，不能一律按 IP 处理。
- 大量用户可能共享同一个出口 IP，过严的 IP 限流会误伤正常用户。
- 限流需要定义突发容量、拒绝方式和客户端重试策略。
- Nginx 限流只能作为入口保护，复杂的业务额度仍应由应用层控制。

## 10. IP 白名单、黑名单与管理入口保护

### 适用场景

- 管理后台只允许办公网络或 VPN 访问。
- 临时封禁恶意来源地址。
- 内部监控、诊断或运维接口不应公开访问。
- 某些合作方接口只允许固定出口地址访问。

### 解决的问题

在请求进入应用之前按来源地址进行基础访问控制，可以缩小敏感入口的暴露范围。

### 注意事项

- Nginx 必须能够识别真实客户端 IP。经过 CDN 或其他代理后，直接看到的可能只是代理节点地址。
- IP 地址可能变化，白名单需要维护机制。
- IP 控制不能代替登录认证、多因素认证和细粒度授权。
- 错误配置可能把管理员自己拒之门外，应保留安全的回滚方式。

## 11. 上传文件与大请求体

### 适用场景

- 用户上传图片、视频、安装包、备份文件或数据文件。
- 默认请求体限制无法满足业务需要。
- 上传过程较长，需要调整读取和转发时间。

### 解决的问题

针对上传接口单独设置请求体大小、超时和临时文件策略，可以避免小请求和大文件上传共用不合适的限制。

### 注意事项

- 不要为了少数上传接口而全站放开请求体大小。
- 应同时检查应用服务器、网关和云负载均衡器的限制。
- 上传文件需要在应用层进行类型、大小、权限和恶意内容检查。
- 超大文件或不稳定网络场景更适合分片上传、断点续传或直接上传对象存储。

## 12. WebSocket、SSE 与长连接代理

### 适用场景

- 即时聊天、在线协作、实时通知、行情推送。
- 浏览器与服务器之间需要保持 WebSocket 长连接。
- 使用 Server-Sent Events 持续向客户端推送事件。
- 普通 HTTP 请求的默认超时会中断长时间连接。

### 解决的问题

为长连接保留必要的协议升级信息，并设置符合业务特点的连接超时，可以避免连接被代理层提前关闭。

### 注意事项

- WebSocket、SSE 和普通短请求的连接特征不同，最好分别设置路由和超时。
- 长连接会持续占用连接资源，需要评估最大并发量。
- 多实例场景下，应考虑消息广播、连接状态和后端实例切换。
- 不能用无限超时掩盖应用无响应问题。

## 13. gRPC 服务代理

### 适用场景

- 微服务或客户端通过 gRPC 通信。
- 希望统一提供 TLS、域名、日志和流量入口。
- 多个 gRPC 服务需要根据路径或服务名路由。

### 解决的问题

Nginx 可以作为 gRPC 服务入口，集中处理连接、安全和转发策略。

### 注意事项

- gRPC 基于 HTTP/2，不能完全照搬普通 HTTP 反向代理的处理方式。
- 应考虑流式调用、长连接、消息大小和超时。
- 错误状态需要保持 gRPC 语义，避免被普通 HTML 错误页替代。

## 14. 跨域请求处理

### 适用场景

- 浏览器中的前端页面需要访问不同域名或端口的 API。
- 希望在统一入口集中添加跨域响应头。
- 需要处理浏览器发送的预检请求。

### 解决的问题

Nginx 可以统一处理简单的跨域策略，减少多个后端重复添加响应头。

### 注意事项

- 允许来源、方法、请求头和凭证必须与业务安全要求一致。
- 使用凭证时不能随意允许所有来源。
- 复杂的动态授权通常应由应用处理，而不是仅靠静态代理规则。
- 跨域错误经常由多层重复添加响应头造成，应确定唯一负责层。

## 15. HTTP 跳转与 URL 规范化

### 适用场景

- HTTP 统一跳转 HTTPS。
- 旧域名迁移到新域名。
- 旧页面路径迁移后仍需兼容搜索引擎和用户收藏。
- 统一是否使用 `www`、大小写或尾部斜杠。

### 解决的问题

跳转可以将多个旧入口统一到正式地址，减少重复内容，并保持旧链接继续可用。

### 注意事项

- 永久跳转可能被浏览器和搜索引擎长期缓存，发布前应充分测试。
- 必须避免两个规则相互跳转形成循环。
- 跳转时应明确是否保留路径和查询参数。
- 内部转发与客户端跳转不是同一件事：前者客户端地址不变，后者客户端会重新发起请求。

## 16. 自定义错误页与维护页

### 适用场景

- 后端服务维护期间展示统一提示页面。
- 发生 404、服务器错误或上游不可用时，不希望暴露默认错误页面。
- 系统发布期间需要临时阻止普通用户访问。

### 解决的问题

统一错误页可以改善用户体验，隐藏不必要的服务器信息，并在故障期间提供明确说明。

### 注意事项

- 错误页必须自身可访问，不能依赖已经故障的后端服务。
- 应保留正确的 HTTP 状态码，不能所有错误都返回成功状态。
- API 请求通常更适合返回结构化错误，而不是 HTML 页面。
- 维护模式要为管理员、健康检查或发布系统保留必要入口。

## 17. 访问日志与问题排查

### 适用场景

- 分析访问量、响应时间、状态码和来源地址。
- 排查请求到底停在 Nginx 还是后端应用。
- 识别慢接口、异常流量和频繁错误。
- 为审计、安全分析或监控平台提供数据。

### 解决的问题

合理的访问日志可以记录请求经过入口时的关键状态，帮助定位性能、可用性和安全问题。

### 注意事项

- 建议记录请求总耗时和上游处理耗时，以区分代理耗时与应用耗时。
- 不应记录密码、令牌、Cookie、身份证号等敏感信息。
- 日志必须配置轮转、保留周期和磁盘空间监控。
- 高流量环境需要评估日志写入造成的磁盘压力。

## 18. 多环境与多站点隔离

### 适用场景

- 一台入口服务器承载多个域名和站点。
- 开发、测试、预发布和生产环境需要不同入口。
- 不同业务需要独立证书、日志、限流和代理目标。

### 解决的问题

按站点和环境拆分配置，可以降低规则互相影响的风险，便于独立发布和维护。

### 注意事项

- 不同环境不能共享敏感证书、密钥或后端地址。
- 默认站点应拒绝或安全处理未知域名。
- 公共配置可以复用，但不要让过度抽象降低可读性。
- 修改一个站点前仍需验证整体配置，避免影响同一 Nginx 实例上的其他站点。

## 19. 选择场景时的基本原则

在增加 Nginx 配置之前，可以依次确认以下问题：

1. 请求是静态资源、普通 HTTP、文件上传，还是长连接？
2. Nginx 后面是一台应用服务器，还是多个实例？
3. 是否需要 HTTPS，证书由哪一层管理？
4. 是否需要保留客户端真实 IP、原始域名和协议？
5. 请求能否缓存，是否包含用户私有数据？
6. 后端能够承受多少流量，是否需要限流或并发保护？
7. 超时是正常业务特征，还是后端性能问题？
8. 故障时应返回错误、旧缓存、维护页，还是切换到备用实例？
9. 日志中需要哪些排障字段，哪些敏感信息绝对不能记录？
10. 配置变更失败时，如何验证和快速回滚？

## 20. 常见误区

- **把 Nginx 当成万能安全层**：入口限制只能减少风险，应用仍必须做好认证、授权、输入校验和数据保护。
- **全站使用同一超时**：普通接口、上传、下载和长连接的超时需求不同。
- **为了方便而无限放大限制**：请求体、连接数和超时过大，会放大资源耗尽风险。
- **盲目启用缓存**：用户数据或权限相关响应被共享缓存，可能造成严重的数据泄露。
- **只配置转发，不传递原始请求信息**：会导致客户端 IP、协议和域名判断错误。
- **只做负载均衡，不考虑应用状态**：本地会话和本地文件会使请求切换实例后出现异常。
- **修改后直接重启**：应先验证配置语法和依赖文件，再平滑加载，并准备回滚方案。
- **忽略默认站点**：未知域名可能被错误地转发到正式系统。

## 总结

Nginx 最常见的角色包括静态资源服务器、反向代理、负载均衡入口、HTTPS 终止点和基础流量治理层。配置设计应围绕具体使用场景展开：先明确请求类型、业务容量、安全边界和故障处理方式，再选择必要能力。配置越复杂，越需要拆分职责、保留日志、验证变更并准备回滚。
