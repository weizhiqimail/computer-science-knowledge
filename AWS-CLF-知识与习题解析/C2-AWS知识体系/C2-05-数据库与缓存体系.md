## 3-★★★★★-数据库基础与数据模型
### 3.1-Database-是什么？

Database

=

```text
数据库
```

最简单地说：

```text
Database
不是单纯“一个装数据的文件”。

它还提供一套规则和能力，
让 Application 能够高效、可靠地组织、查询、修改数据。
```

例如：

```text
Application
     │
     │ SQL / API
     ▼
Database Engine
     │
     ├── Data Model
     ├── Query
     ├── Index
     ├── Transaction
     ├── Concurrency
     └── Persistence
```

---

### 3.2-Storage-与-Database-到底有什么区别？

例如：

```text
S3
```

当然可以存：

```text
orders.json
```

但是如果有：

```text
10 亿订单
```

然后每秒都需要：

```text
SELECT ...
UPDATE ...
按 user_id 查
按 status 查
事务提交
```

仅仅把 JSON 文件放 S3，

并不等于已经获得一个 Online Transaction Database。

所以：

```text
Storage
解决：
字节放在哪里

Database
解决：
业务数据如何建模、查询、修改和保证正确性
```

---

Engine

```text

```

=

```text
数据库引擎
```

例如：

```text
MySQL
PostgreSQL
MariaDB
Oracle Database
Microsoft SQL Server
IBM Db2
```

这些不是“一个硬盘”。

它们是完整数据库软件系统。

### 3.6-★★★★★-Relational-Database-是什么？

Relational Database

=

```text
关系数据库
```

核心数据结构通常是：

```text
Table
Row
Column
```

例如：

#### 3.6.1-users

| user_id | name | email |
|---|---|---|
| 1001 | Alice | a@example.com |
| 1002 | Bob | b@example.com |

#### 3.6.2-orders

| order_id | user_id | amount |
|---|---|---:|
| 90001 | 1001 | 8000 |
| 90002 | 1001 | 12000 |

这里：

```text
users.user_id
```

和：

```text

```

之间就存在业务关系。

### 3.8-Primary-Key-与-Foreign-Key

Primary Key

简称：

```text
PK
```

中文：

```text
主键
```

用于唯一标识一条记录。

例如：

```text
order_id = 90001
```

Foreign Key

简称：

```text
FK
```

中文：

```text
外键
```

用于表达表之间的关系。

例如：

```text
orders.user_id
→ users.user_id
```

注意：

```text
Database Key
```

和：

```text
KMS Encryption Key
```

完全不是一个概念。

---

### 3.9-★★★★★-SQL-是什么？

SQL

=

```text
Structured Query Language
结构化查询语言
```

关系数据库常用 SQL。

例如：

```sql
SELECT *
FROM orders
WHERE user_id = 1001;
```

更新：

```sql
UPDATE orders
SET status = 'PAID'
WHERE order_id = 90001;
```

CLF-C02 不要求写复杂 SQL。

只需要知道：

```text
SQL
→ Relational Database
→ Table / Row / Column / Relationship
```

---

### 3.10-Transaction-是什么？

Transaction

=

```text
事务
```

例如支付过程：

```text
1. 创建支付记录
2. 扣减库存
3. 修改订单状态
4. 记录账务
```

业务通常希望：

```text
要么整体成功
要么整体失败 / 回滚
```

而不是：

```text
钱扣了
订单却没更新
```

这就是 Transaction 思想。

---

### 3.11-ACID-是什么？

ACID 是关系型事务里常见的四个性质：

```text
A = Atomicity
C = Consistency
I = Isolation
D = Durability
```

中文：

```text
Atomicity   原子性
Consistency 一致性
Isolation   隔离性
Durability  持久性
```

CLF-C02 不要求深入数据库理论，

但要知道：

```text
订单
支付
财务
库存
```

这类有明确关系和事务要求的数据，

关系数据库通常很自然。

---

### 3.12-★★★★★-NoSQL-是什么？

NoSQL

常被解释为：

```text
Not Only SQL
```

它不是简单等于：

```text
“不能查询”
```

也不是：

```text
“没有结构”
```

更准确的学习方式：

```text
不把所有业务都强制建模为传统关系表 + Join。
```

NoSQL 有多种模型：

```text
Key-Value
Document
Graph
Wide-column
...
```

AWS CLF-C02 中最核心：

```text
DynamoDB
→ Key-Value / Document NoSQL

DocumentDB
→ Document Database

Neptune
→ Graph Database
```

---

### 3.13-为什么需要-NoSQL？

假设 GlobalShop 购物车：

```text
user_id
→ cart data
```

访问模式很简单：

```text
给我 user_id
→ 返回购物车
```

而系统可能面对：

```text
几千万用户
流量快速变化
大规模并发
```

如果主要需求并不是复杂 Join，

可以考虑：

```text
Key-Value / NoSQL
```

这不是说：

```text
NoSQL 一定比 SQL 好
```

而是：

```text
Workload 不同
→ Data Model 可以不同
```

---

### 3.14-Database-选择的第一原则：Access-Pattern

Access Pattern

=

```text
访问模式
```

也就是：

```text
Application 到底怎么读写数据？
```

例如：

```text
按订单 ID 查
按用户查最近 20 个订单
按商品 ID 读详情
按用户 ID 读购物车
查询人与人的关系
复杂 BI 聚合
```

不同 Access Pattern 可能对应不同数据库技术。

所以：

```text
不是先问：
AWS 哪个 Database 最强？

而是先问：
我的数据是什么，
我要怎么访问？
```

### 4.9-★★★★★-RDS-Multi-AZ

Multi-AZ

=

```text
Multiple Availability Zones
多可用区
```

核心目的：

```text

```

经典 RDS Multi-AZ DB Instance 思路：

```text
              Application
                   │
                   ▼
                Endpoint
                   │
             Primary DB
                AZ-A
                   │
        synchronous replication
                   │
                   ▼
              Standby DB
                AZ-B
```

如果 Primary 出现问题：

```text
Failover
↓
Standby 接管
```

---

### 4.10-Standby-是什么？

Standby

=

```text
备用
待机
```

经典 Multi-AZ DB Instance 中：

```text
Standby
```

主要是：

```text
HA / Failover
```

不是为了：

```text
给 Application 分担读请求
```

这是考试非常重要的区别。

---

### 4.11-★★★★★-Read-Replica

Read Replica

=

```text
只读副本 / 读取副本
```

核心目的：

```text
Read Scaling
```

架构：

```text
              Primary
             /       \
            /         \
           ▼           ▼
    Read Replica  Read Replica
```

Application 可以把：

```text
读流量
```

分到 Replica。

---

### 4.12-★★★★★-Multi-AZ-vs-Read-Replica

这是数据库章节最重要的对比之一。

| 能力 | Multi-AZ | Read Replica |
|---|---|---|
| 主要目标 | High Availability | Read Scaling |
| 故障切换 | 是核心用途 | 不是主要定义 |
| 是否分担读请求 | 经典 Standby 不用于普通读流量 | 是 |
| 关键词 | failover、HA | read-heavy、scale reads |

最简单：

```text
Multi-AZ
→ 坏了怎么办？

Read Replica
→ 读太多怎么办？
```

---

### 4.13-一个当前-AWS-细节：不要把所有-Multi-AZ-形态混成一个

[UPDATED]

现在 RDS 不只有最经典的：

```text
Multi-AZ DB instance deployment
```

也存在：

```text
Multi-AZ DB cluster
```

等形态。

其中 Reader Instance / Read Replica 的能力比旧教材中的一句：

```text
“Multi-AZ 永远不能读”
```

要复杂。

所以本教材在 CLF-C02 基础层统一采用更准确表述：

```text
经典 Multi-AZ DB Instance 的 Standby
主要用于 HA / Failover，
不能拿 Standby 当普通 Read Replica 使用。
```

考试如果明确说：

```text
read scaling
```

应关注：

```text
Read Replica
```

如果明确说：

```text
automatic failover / high availability
```

应关注：

```text
Multi-AZ
```

## 5-★★★★★-Amazon-Aurora
### 5.1-★★★★★-Amazon-Aurora

[CURRENT-IN-SCOPE]

正式名称：

```text
Amazon Aurora
```

中文一般直接称：

```text
Amazon Aurora
```

Aurora

原本是：

```text
极光
```

这是产品名，

不像 RDS 那样是缩写。

---

### 5.2-Aurora-到底是什么？

AWS 当前定义：

```text
Fully Managed Relational Database Engine
```

并且兼容：

```text
MySQL
PostgreSQL
```

所以：

```text
Aurora
不是 NoSQL

Aurora
不是 MongoDB

Aurora
不是 Data Warehouse
```

它是：

```text
Relational Database
```

---

### 5.3-Aurora-与-RDS-的关系

容易出现两个错误极端。

错误 1：

```text
Aurora 就是 RDS 的另一个普通第三方 Engine
```

不够准确。

错误 2：

```text
Aurora 和 RDS 完全没关系
```

也不对。

更好的理解：

```text
Amazon RDS
关系数据库托管体系
│
├── MySQL
├── PostgreSQL
├── MariaDB
├── Oracle
├── SQL Server
├── Db2
│
└── Amazon Aurora
     ├── MySQL-compatible
     └── PostgreSQL-compatible
```

Aurora 有自己专门设计的：

```text
Distributed Storage Architecture
Cluster
Reader / Writer
```

---

### 5.4-Aurora-Cluster

Aurora 的一个重要概念：

```text
DB Cluster
```

简化：

```text
                 Aurora Cluster
                       │
          ┌────────────┴────────────┐
          │                         │
          ▼                         ▼
      Writer                     Reader
     Instance                   Instance
          │                         │
          └──────────┬──────────────┘
                     ▼
             Shared Cluster Storage
```

用户不需要像自己搭 MySQL 集群那样，

自己管理底层分布式存储复制。

---

### 5.5-Writer-与-Reader

Writer

=

```text
写入节点
```

负责：

```text
Read / Write
```

Reader

=

```text
读取节点
```

用于：

```text
Read Scaling
```

所以 Aurora 同样体现：

```text
Write Path
Read Scaling
High Availability
```

---

### 5.6-Aurora-为什么经常出题？

因为它很容易和：

```text
RDS
DynamoDB
Redshift
```

混淆。

题目看到：

```text
MySQL-compatible
PostgreSQL-compatible
relational
AWS-managed
high availability
```

Aurora 可能是重点候选。

看到：

```text
NoSQL
key-value
serverless at any scale
```

应该更偏：

```text
DynamoDB
```

---

### 5.7-RDS-vs-Aurora

可以这样理解：

```text
RDS
→ Managed Relational Database Service 家族

Aurora
→ AWS 自研的 MySQL/PostgreSQL-compatible
  Managed Relational Database Engine
```

如果企业必须使用：

```text
Oracle
SQL Server
Db2
MariaDB
```

Aurora 显然不是对应答案。

### 6.5-Partition-Key-是什么？

Partition

=

```text
分区
```

Partition Key

```text
“业务主键的另一个名字”
```

```text

```

例如：

```text

```

访问：


### 6.6-Sort-Key-是什么？

Sort Key

=

```text
排序键
```

Composite Primary Key：

```text
Partition Key
+
Sort Key
```

例如：

```text

```

可以把：

```text

```

CLF-C02 不要求深入 Single-table Design，

但要知道：

```text
DynamoDB
不是传统 Row / Foreign Key / Join 思维的直接复制。
```

### 7.2-★★★★★-Cache-是什么？

Cache

=

```text
缓存
```

缓存的核心：

```text
把“经常使用、读取成本较高”的数据
放到更快的位置，
减少对后端系统的访问。
```

例如：

```text
Application
    │
    ▼
ElastiCache
    │
    │ cache miss
    ▼
RDS
```

---

### 7.3-为什么-Database-前面还需要-Cache？

假设商品详情：

```text

```

一秒被请求：

```text
100,000 次
```

如果每一次都：

```text
Application
↓
RDS
↓
复杂 Query
```

数据库压力会很大。

可以：

```text
第一次：
Application
↓
RDS
↓
结果放 Cache

以后：
Application
↓
Cache
↓
快速返回
```

---

### 7.4-Cache-Hit-与-Cache-Miss

Cache Hit

=

```text
缓存命中
```

即：

```text
需要的数据在 Cache 里
```

Cache Miss

=

```text
缓存未命中
```

即：

```text
Cache 没有
↓
去 Database / Backend 读取
```

这两个词以后会经常出现。

---

### 7.5-Cache-Aside-Pattern

一个非常常见的缓存模式：

```text
Application
     │
     ▼
Check Cache
     │
     ├── Hit
     │    └── Return
     │
     └── Miss
          │
          ▼
        Database
          │
          ▼
      Put Cache
          │
          ▼
        Return
```

叫：

```text

```

CLF 不要求实现代码，

但这个图能解释：

```text
为什么 ElastiCache 能降低 Database Load
```


两类运行方式。

这也是一个当前状态需要注意的点：

### 7.8-ElastiCache-最大的理解误区


不对。




### 7.9-Cache-Invalidation-为什么重要？

Invalidation

=

```text

```

例如：



```text

```

所以 Cache 不是：

```text
“加上以后系统一定更简单”
```

它会引入：

```text

```

等问题。

CLF 不要求设计完整一致性方案，

但需要知道：

```text

是性能优化层，
不是免费的魔法。
```

### 12.3-常见错误-1：NoSQL-=-没有-Schema

不准确。

```text

Index
```

DocumentDB 也有：

```text
Document Structure
Index
Query Pattern
```

区别是：

```text
数据模型
不是传统关系表设计的简单复制
```


### 12.6-常见错误-4：ElastiCache-=-永久数据库替代品

典型用于：


很多业务仍需要：

```text
Durable Source of Truth
```

### 13.9-最重要的八句话

```text

4. Read Replica 的核心是 Read Scaling。
5. DynamoDB = Serverless Fully Managed NoSQL，核心是 Key-Value / Document。
6. ElastiCache = In-Memory Cache，用来降低 Latency 和 Database Load。
7. DocumentDB = MongoDB-compatible Document Database；Neptune = Graph Database。
8. Redshift = Data Warehouse，不是普通 OLTP RDS。
```
